# 周期维护窗口的时区边界

周期维护窗口用于在计划维护期间延迟告警通知。时间边界错误会导致维护结束后仍然没有通知，或在约定的维护期间提前通知。

## 输入和存储

创建请求中的 `startsAt`、`endsAt` 和 `recurrenceUntil` 均携带 UTC 偏移。服务将其保存为 UTC 时间，`timeZone` 保存 IANA 时区名称。

首个窗口采用请求明确指定的起止瞬间。秋季时钟回拨时，同一当地时间出现两次，例如纽约的 `2026-11-01T01:30:00-04:00` 和 `2026-11-01T01:30:00-05:00` 相差一小时。系统不能把后者重新解析为前者。

之后的窗口按指定时区的当地日期重复。每天或每周的重复时段遵循当地钟表时间，因此跨夏令时的实际持续秒数可能变化。

## 夏令时解析规则

| 场景 | 行为 |
| --- | --- |
| 首个窗口位于重复时段 | 保留提交的起止偏移对应的确切瞬间 |
| 后续窗口遇到不存在的当地时间 | 遵循 Java 时区规则，向前移动该边界一个时间缺口 |
| 只有开始时间落在缺口中 | 独立解析结束时间，不额外推迟有效的结束边界 |
| 后续窗口遇到重复时段 | 保持原有规则，选择较早的有效偏移 |
| 两个边界都位于缺口中 | 两个边界分别解析，保留其当地间隔 |
| 解析后开始不早于结束 | 当次没有有效窗口，不额外制造一个静默时段 |
| 周期截止落在窗口中 | 在 `recurrenceUntil` 截止 |

开始边界包含在窗口内，结束边界不包含。每周重复仍只在指定 ISO 星期启动；首个日期未被选中时不会额外启动窗口。

解析依据：[Java 21 ZonedDateTime](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/ZonedDateTime.html)。无偏移的缺口和重复时段遵循该标准库的现有解析行为。

## 可复现场景

纽约每日窗口的初始值为 2026-03-07 02:30 至 04:00，时区为 `America/New_York`。

2026-03-08 进入夏令时，02:30 不存在，开始时间按标准库规则调整到 03:30。04:00 是有效时间，结束时间仍为 04:00。修复前，结束时间从调整后的开始时间计算，错误变为 05:00，通知额外延迟一小时。

另一个场景是首个窗口明确选择 2026-11-01 的第二个 01:15 至第二个 01:45，即两个值均使用 `-05:00`。该窗口应在 UTC 06:15 至 06:45 生效。修复前，重复解析丢失指定偏移，窗口被过滤掉。

## 本地验证

在 `server` 目录使用 Java 21 执行：

```bash
mvn -B -ntp -Dtest=AlertSilenceScheduleTest,AlertSilenceDstTest,AlertSilenceServiceTest,RecurringSilenceNotificationTest,NotificationOutboxServiceTest test
```

测试覆盖纽约一小时缺口、Lord Howe 半小时缺口、首个窗口的重复时段偏移、后续重复时段、跨日每周窗口、亚秒边界以及通知入队截止时间。通知测试使用真实创建服务和时间计算，仅替换持久化边界，不发送外部消息。

## 兼容和回滚

无迁移，直接替换时间计算。没有新增配置、依赖或数据库字段，既有 UTC 值和时区标识继续使用。

非夏令时窗口、每周星期选择及后续重复时段的默认偏移策略保持原有含义。回滚对应修复提交即可恢复旧计算，但上述缺陷也会恢复。
